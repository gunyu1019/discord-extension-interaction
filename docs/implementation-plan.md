# Discord Interaction 지원 확장 작업 계획

이 문서는 Discord의 Interactions Overview, Receiving and Responding, Application Commands,
Components Overview, Component Reference, Using Message Components, Using Modal Components를
프레임워크 자체 API의 지원 범위로 삼는다. 이미 제공 중인 공개 이름은 유지하고,
새 공개 이름과 필드는 Discord API 용어를 따른다.

## 작업 원칙

- 각 번호의 하위 작업은 검토 가능한 결과와 검증 방법을 갖춘 별도 로컬 커밋으로 끝낸다.
- 커밋 직전에 `git log`와 `git status`를 확인하고, 해당 작업의 파일만 스테이징한다.
- 작업 시작 전에 존재하던 변경은 확인 후 기준선 커밋 `edd5ac9`에 포함했다.
- 기존 공개 이름은 그대로 유지한다. 새 정책을 명시하지 않은 범위에는 자동 동기화를 적용하지 않는다.
- 도메인 모델은 Discord API 데이터 구조를 표현하고, 애플리케이션 계층은 동기화와
  디스패치를 담당하며, Gateway·HTTP 전송과 payload 직렬화는 기반 계층으로 분리한다.
  `client.py`와 `components.py`에 모든 로직을 계속 추가하지 않는다.
- `discord.py`의 내부 구현에 접근하는 코드는 전송 어댑터에만 둔다.
- 한 유형의 지원은 생성, 직렬화, 수신, 결과 해석 및 실패 사례의 검증을 포함한다.

## 확정된 결정

1. 기존 작업 트리의 변경을 확인한 뒤 기준선 커밋에 포함했다.
2. 이미 개발된 공개 API 이름은 유지하고 새 기능만 Discord API 용어를 사용한다.
3. 새 `SyncCommand` 정책이 없는 범위에는 자동 동기화를 수행하지 않는다.
   기존 `global_sync_command=True`나 개별 `sync_command=True`는 명시적 설정으로 취급하며,
   기존 인자의 연결 방식은 3-g에서 검증한다.
4. 기존 메시지 API의 단일 Button·Selection은 전송 시 각각 ActionRow로 감싼다.
   사용자가 전달한 객체와 목록은 변경하지 않는다.
5. 새 명령 범위는 `GlobalScope()`·`GuildScope(guild_id)` 및 `scope=`로 선언한다.
   기존 `guild_id=` 인자는 유지하되 충돌하는 동시 지정은 거부한다.
6. 새 `SyncCommand`는 범위별 메모리 정책이며 생략한 create/edit/delete는 모두 True다.
   같은 범위의 기존 `global_sync_command`보다 새 정책을 우선한다.
