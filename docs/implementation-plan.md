# Discord Interaction 지원 확장 작업 계획

이 문서는 Discord의 Interactions Overview, Receiving and Responding, Application Commands,
Components Overview, Component Reference, Using Message Components, Using Modal Components를
프레임워크 자체 API의 지원 범위로 삼는다. 새 공개 이름과 필드는 Discord API 용어를 따른다.

## 작업 원칙

- 각 번호의 하위 작업은 검토 가능한 결과와 검증 방법을 갖춘 별도 로컬 커밋으로 끝낸다.
- 커밋 직전에 `git log`와 `git status`를 확인하고, 해당 작업의 파일만 스테이징한다.
- 기존 작업 트리의 변경은 소유자가 결정하기 전까지 스테이징하지 않는다.
- 공개 API의 호환성 정책과 자동 동기화 기본값은 사용자 결정 후 확정한다.
- 도메인 모델은 Discord API 데이터 구조를 표현하고, 애플리케이션 계층은 동기화와
  디스패치를 담당하며, Gateway·HTTP 전송과 payload 직렬화는 기반 계층으로 분리한다.
  `client.py`와 `components.py`에 모든 로직을 계속 추가하지 않는다.
- `discord.py`의 내부 구현에 접근하는 코드는 전송 어댑터에만 둔다.
- 한 유형의 지원은 생성, 직렬화, 수신, 결과 해석 및 실패 사례의 검증을 포함한다.

## 0. 계약과 지원 범위

- [ ] **0-a 계획 고정:** 0~9단계의 하위 작업, 의존 관계, 완료 기준을 기록한다. 검증: 문서 리뷰.
- [ ] **0-b 기능 목록:** 공식 문서의 명령 유형, 컴포넌트 유형, 상호작용 유형, 응답 유형,
      공통 필드를 표로 만들고 현재 구현의 지원 상태와 코드 위치를 기록한다. 검증: 누락 유형 번호 대조.
- [ ] **0-c 용어 계약:** Discord API 이름과 Python 공개 이름의 대응표를 정하고 기존 이름의
      별칭·사용 중단 정책을 기록한다. 검증: 공개 API 목록 리뷰.
- [ ] **0-d 경계 설계:** `domain`, `application`, `serialization`, `transport`, 공개 facade 사이의
      의존 방향과 데이터 흐름을 설계 결정 문서로 기록한다. 검증: import 방향 리뷰.
- [ ] **0-e 호환 범위:** Python, `discord.py`, 기존 생성자와 데코레이터의 지원 범위를 정한다.
      검증: 설치 메타데이터와 예제의 일치 여부 확인.

## 1. 기존 동작 안정화

- [ ] **1-a 기준선:** 기존 테스트를 실행하고 기존 예제의 주요 공개 사용법을 회귀 테스트로 보존한다.
- [ ] **1-b 하위 명령 그룹:** 그룹의 중첩 옵션을 따라 실제 하위 명령을 찾도록 수정한다.
      검증: 일반·그룹 하위 명령 호출 테스트.
- [ ] **1-c 컴포넌트 필터:** 선언된 컴포넌트 클래스를 유형 번호와 올바르게 비교한다.
      검증: 같은 `custom_id`의 다른 유형이 잘못 실행되지 않는 테스트.
- [ ] **1-d 명령 옵션:** Mentionable과 Attachment를 `resolved` 데이터에서 변환한다.
      검증: 사용자·역할·첨부 파일 및 누락 데이터 테스트.
- [ ] **1-e 관리 메서드:** setup hook 제거와 ID 기준 명령 캐시 조회를 고친다.
      검증: 추가/제거 및 캐시 적중 테스트.
- [ ] **1-f 예제 정합성:** README의 버전 요구사항과 오래된 공개 이름을 실제 코드에 맞춘다.
      검증: 예제 import와 문서 코드 블록 검사.

## 2. 명령 정의와 범위

- [ ] **2-a 범위 모델:** GlobalScope와 GuildScope를 도메인 값으로 정의하고 ID를 검증한다.
- [ ] **2-b 명령 키:** `(scope, type, name)`을 명령 식별자로 정해 로컬 레지스트리와 원격 목록에 적용한다.
- [ ] **2-c 명령 메타데이터:** NSFW, 기본 권한, 설치 유형, 실행 컨텍스트의 입력 모델을 정리한다.
- [ ] **2-d 현지화:** 명령·하위 명령·옵션·선택지의 이름/설명 현지화를 직렬화하고 역직렬화한다.
- [ ] **2-e 서버별 전송:** 서버별 명령의 생성·목록·조회·수정·삭제를 전송 어댑터에 추가한다.
- [ ] **2-f 비교 규칙:** 서버가 할당한 ID·버전을 제외하고 실제 선언 필드를 비교한다.
- [ ] **2-g 공개 선언:** 데코레이터와 직접 생성 방식 모두 범위와 메타데이터를 선언할 수 있게 한다.
      검증: 두 방식이 같은 등록 payload를 만든다.

## 3. SyncCommand 정책과 동기화

- [ ] **3-a 정책 모델:** `SyncCommand(create, edit, delete)`를 불변 객체로 만들고 각 값의 의미를 고정한다.
- [ ] **3-b 정책 저장:** 전역·서버별 정책을 독립적으로 보관하고 필요한 직렬화/복원 경계를 정한다.
- [ ] **3-c 계획 생성:** 로컬과 원격 명령을 비교해 Create/Edit/Delete/Unchanged 작업을 담는 SyncPlan을 만든다.
- [ ] **3-d 계획 적용:** 정책이 허용한 작업만 실행하고 적용 결과·실패를 구조화해 반환한다.
- [ ] **3-e 자동 실행:** 시작·재연결 시 중복 실행 없이 설정된 범위의 계획만 적용한다.
- [ ] **3-f 수동 실행:** 범위별 계획 조회와 명시적 적용 API를 제공한다.
- [ ] **3-g 기존 설정 연결:** `global_sync_command` 및 기존 개별 `sync_command` 인자의 의미를
      결정된 호환성 정책에 따라 새 정책으로 연결한다.
- [ ] **3-h 안전성 검증:** 정책의 8가지 조합, 범위 분리, 부분 실패, 삭제 후보 목록을 테스트한다.

## 4. 인터랙션과 응답의 공통 구조

- [ ] **4-a 공통 데이터:** 원본 payload와 공통 메타데이터를 보존하는 도메인 모델을 만든다.
- [ ] **4-b resolved 해석:** 사용자·멤버·역할·채널·메시지·첨부 파일을 공통 resolver에서 해석한다.
- [ ] **4-c 디스패처:** Gateway 이벤트 처리와 명령/컴포넌트/모달 실행을 분리한다.
- [ ] **4-d 응답 상태:** 초기 응답, 지연, 원본 수정, 후속 응답의 상태 전이를 정의한다.
- [ ] **4-e 응답 전송:** callback과 webhook 요청 생성 로직을 전송 어댑터로 모은다.
- [ ] **4-f 경계 검증:** 중복 초기 응답, 만료 토큰, 첨부 파일, 실패한 요청의 상태를 테스트한다.

## 5. 컴포넌트 공통 모델

- [ ] **5-a 기본 계약:** `type`, 선택적 `id`, `to_payload`, `from_payload`를 정의한다.
- [ ] **5-b 유형 등록:** 유형 번호와 모델/파서를 연결하는 등록표를 만든다.
- [ ] **5-c 알 수 없는 유형:** 원본 필드를 보존하는 UnknownComponent를 만든다.
- [ ] **5-d 기존 유형 이전:** Action Row, Button, String Select, Text Input, Label을 개별 모듈로 나눈다.
- [ ] **5-e 구조 검증:** 메시지/모달별 허용 위치, 개수, 필수 필드를 검증한다.
- [ ] **5-f 호환 facade:** 기존 공개 생성자와 `to_dict`의 동작을 결정된 정책에 맞게 연결한다.
- [ ] **5-g 왕복 검증:** 기존 유형과 알 수 없는 유형의 직렬화·역직렬화 테스트를 추가한다.

## 6. 메시지 Components V2

- [ ] **6-a 텍스트/레이아웃:** Text Display, Section, Container, Separator를 별도 모듈에 구현한다.
- [ ] **6-b 미디어:** Thumbnail, Media Gallery, File과 미디어 항목 모델을 구현한다.
- [ ] **6-c V2 모드:** V2 전송에서 IS_COMPONENTS_V2 플래그를 자동 설정한다.
- [ ] **6-d 필드 검증:** V2에서 사용할 수 없는 기존 메시지 필드와 컴포넌트 수를 검증한다.
- [ ] **6-e 송수신 연결:** 일반 메시지·인터랙션 응답·수정·수신에서 V2 구조를 보존한다.
- [ ] **6-f 파일 연결:** `attachment://` 참조와 multipart 첨부 파일을 함께 처리한다.
- [ ] **6-g 왕복 검증:** 중첩 레이아웃, 미디어, 플래그 및 레거시 공존을 테스트한다.

## 7. 버튼과 선택 메뉴

- [ ] **7-a 버튼 스타일:** 일반·링크·프리미엄 스타일의 custom_id/url/sku_id 규칙을 구현한다.
- [ ] **7-b String Select:** 옵션, 기본값, 모달 required 및 선택 결과를 정리한다.
- [ ] **7-c 자동 선택:** User/Role/Mentionable/Channel Select를 독립 모델로 구현한다.
- [ ] **7-d 기본 선택:** default_values와 Channel Select의 channel_types를 지원한다.
- [ ] **7-e 결과 해석:** values와 resolved를 연결해 선택된 Discord 객체를 반환한다.
- [ ] **7-f 콜백 연결:** 새 유형에도 custom_id 핸들러와 wait_for가 동작하게 한다.
- [ ] **7-g 검증:** 각 유형의 송신·수신·객체 해석과 잘못된 필드 조합을 테스트한다.

## 8. 모달 입력

- [ ] **8-a Label 규칙:** Label 자식 유형과 모달 내 배치 및 길이 제한을 검증한다.
- [ ] **8-b File Upload:** 업로드 개수·형식 필터와 제출 결과의 첨부 파일을 지원한다.
- [ ] **8-c Radio Group:** 옵션 모델, 기본 선택, 제출 value를 지원한다.
- [ ] **8-d Checkbox Group:** 옵션, min/max, 제출 values를 지원한다.
- [ ] **8-e Checkbox:** 기본값과 제출 boolean value를 지원한다.
- [ ] **8-f 모달 선택 메뉴:** 문자열·자동 선택 메뉴의 제출 결과를 보존한다.
- [ ] **8-g 입력 접근:** custom_id로 입력을 찾는 API와 기존 components 목록을 함께 제공한다.
- [ ] **8-h 검증:** 모든 입력 유형의 모달 생성·제출 왕복을 테스트한다.

## 9. 추가 수신 방식, 특수 명령, 통합 검증

- [ ] **9-a HTTP 수신:** Gateway와 같은 디스패처로 보내는 HTTP 어댑터를 추가한다.
- [ ] **9-b 서명과 PING:** Ed25519 검증, 유효하지 않은 요청 거부, PING/PONG을 구현한다.
- [ ] **9-c 응답 방식:** HTTP inline 응답과 callback 요청의 유효한 사용 경로를 정리한다.
- [ ] **9-d Activity:** PRIMARY_ENTRY_POINT 명령과 LAUNCH_ACTIVITY 응답을 지원한다.
- [ ] **9-e 명령 권한:** 별도 인증 요구사항을 가진 서버별 명령 권한 API를 분리한다.
- [ ] **9-f 실서버 점검:** 명령, V2, 선택 메뉴, 모달, 첨부 파일, HTTP 수신을 수동 smoke test한다.
- [ ] **9-g 문서와 배포:** 사용 예제, 이전 안내, 지원 범위 표, CI 검증을 갱신한다.

## 결정 대기

1. 현재 작업 트리의 기존 수정 파일을 기준선 커밋에 포함할지 여부.
2. 기존 Python 공개 이름을 별칭으로 유지할지 여부.
3. 명시적 정책이 없는 범위의 자동 동기화 기본값.

각 결정에 영향을 받지 않는 하위 작업은 먼저 진행한다.
